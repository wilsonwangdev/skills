# 构建可维护的应用

采用本技能的构建约定，把成果做成开发者和 Agent 能继续维护的项目。这些是本技能的默认选择，具体框架、平台及实施范围服从用户要求和现有工程。

## 先确定本次交付范围

区分当前任务是修订技能或规约、准备工程骨架，还是实现应用。用户要求先打磨规则时，只修改规则及隔离试用材料；应用改造留到后续实施任务。骨架阶段如实保留业务功能和运行验收的未完成状态。

实施应用时，读取入口、项目清单、构建、测试和项目约定，确认交付平台、关键交互与数据流。已有工程保留业务行为和未完成工作，迁移按本次范围推进；局部修复不顺带重建工程或升级整个工具链。

## 在业务扩展前建立基线

新项目从适用的官方脚手架开始；整理原型时先在临时目录生成官方模板作比较基线，保留标准入口和配置分工。新建 Web 使用 TypeScript，其他平台沿用其原生类型与工具体系。

从官方资料核对当前稳定版本、运行时要求与依赖兼容性，记录实际选择及锁文件。框架支持的例外需要具体理由，不把历史版本号写成永久规则，也不为了使用最高版本号引入预览版。

**新建 Web 或约定迁移工程基线时，在扩展业务页面前先读取并落实 [Web 工程基线](references/web.md)。** 起点包括严格类型与静态检查、格式配置、可安装且有效的提交前检查、多语言入口、亮色/暗色/跟随系统、可扩展主题和用户偏好，以及多设备下可操作的代表性界面。只安装依赖、声明变量或留下待办不算这些能力已接通。已有项目的普通功能修改沿用当前工程约定，未纳入任务的基线缺口只作说明，不因此扩大改造。

先用一个最小可运行界面验证这些机制，再复用它增加业务。新项目的基线缺失时先补齐当前基础；已有工程的差距按迁移范围说明，不用“后续统一优化”替代已经纳入任务的要求。

独立 Web 应用在确定手机使用方式时，就评估 PWA 的安装、独立窗口、弱网及更新需求，明确本轮落实范围；按 [PWA 与移动使用](references/web.md#pwa-与移动使用) 验证，避免等页面完成后才处理移动使用路径。

## 复用成熟能力，保留业务边界

实现基础能力前，比较框架内置能力、官方集成和维护中的包，核对适配、运行环境及许可。渲染、路由、表单、国际化、主题、解析、校验和测试基础设施优先复用。

自定义代码只补具体业务缺口，说明已有方案不足，把适配限制在接口或数据转换处。通用渲染器、DOM 模拟、测试运行器及解析引擎交给成熟方案；研究机制的任务按研究目标另定范围。

TypeScript/Web 项目以 `package.json` 维护项目身份、版本、运行时、包管理器、依赖及命令，其他平台使用其原生清单。页面、服务和产物需要的元信息从清单衍生；精确依赖与工具版本由清单及包管理器生成的锁文件维护。业务协议、用户偏好与持久化标识保持独立生命周期。

## 让设计和规约持续生效

设计站点入口时，先根据受众选择产品介绍页、应用首页或两者并存；首页要让人理解用途并开始核心任务，也能让回访者继续已有工作。具体判断和验收见 [Web 工程基线](references/web.md#首页与核心路径)。

先选择与产品用途相符的优秀设计参考，说明布局、层级和交互的借鉴，再建立语义设计变量及基础组件。语言、外观模式和主题选择共同作用于同一套组件，避免为不同模式复制页面或组件样式。新增页面复用已经验证的基础。

把可自动约束的要求放进类型、检查及格式配置，提交前检查与 CI 调用项目自身的命令。在 `AGENTS.md` 保留简短入口和按任务读取文档的条件；复杂且重复的流程可作为项目级技能，继续链接同一规则来源。项目规约随仓库提供完整上下文，外部个人技能只作可选开发辅助。Agent 指令不能代替自动检查和运行验收。

README 让使用者迅速知道项目用途和怎样启动；CONTRIBUTING 让贡献者知道怎样检查、提交及说明改动。两者围绕读者下一步行动保留重点，通过链接查阅架构、设计与部署。贡献指南先给一条推荐流程，不重复解释每种工具或测试层，也不把每个例外展开成并列流程。删除重复和常识性说明，不把贡献指南写成第二份工程手册，也不为了缩短首页制造更多文档。命令与版本仍由项目清单维护。

公开源码、示例及项目规约使用通用表达与合成材料。个人身份、机器路径、组织私有流程、凭据及真实私有会话留在本地或专用配置；公开前检查跟踪文件与输出产物，忽略规则本身不证明信息已清除。

## 用实际结果完成交付

执行当前范围适用的安装、检查、测试和构建，验证关键交互。建立工程或改变提交链时，在隔离 Git 仓库证明真实违规会阻止提交、修正后能提交，并保护部分暂存的改动。

交付时简述官方基线、必要自定义适配、实际结果与未覆盖范围。规则修订使用代表性请求做独立试用，检查产物和决策；格式或一次骨架试用通过不等于完整应用符合要求。技能不扩大推送、发布、部署或账户操作的授权。

## 从应用实践回馈技能

用户要求把建议沉淀为技能时，先提炼适用条件和可观察的验收标准、修订技能，再应用到当前项目观察效果；实践发现偏差后继续修订。故障先核实真实行为。判断原因属于通用决策、项目约定还是所选工具版本：通用规则回到本技能，项目事实留在项目，版本细节通过官方资料和兼容验证处理。经验回馈采用自包含的合成案例，不携带使用项目的身份、目录、提交及验收日志；技能与项目各自维护完整上下文。优先修正已有规则的歧义或验收条件，不为每个案例增加一条永久要求。

用修订后的技能重做对应任务，检查实际产物。将可迁移的失败路径整理成可复用案例；本次技能试用的版本、输出和边界留在提交评审或独立运行产物中，应用测试统计留在应用验收中。规则、应用验证和安装副本是不同交付项；同步仓库维护源与实际使用副本后再说明完成情况。
