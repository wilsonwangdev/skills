# Web 工程基线

用于新建 Web 或系统整理原型。以下是本技能的默认工程选择；已有框架沿用其官方体系，实施范围以当前任务为准。

## TypeScript 与官方工具链

默认采用当前稳定且相互兼容的 Node.js、pnpm、Vite、TypeScript、Oxlint、Oxfmt 和 Vitest。新建时核对最新稳定发布、运行时及兼容要求；采用较早稳定线需要具体兼容或部署理由，将实际版本锁在项目清单和锁文件。使用官方 TypeScript 模板，依据需求选择框架；已有 Next.js 等完整框架沿用自身脚手架。

第一方界面、服务、共享模块、测试和必要开发脚本使用 `.ts`/`.tsx`，配置优先采用工具正式支持的 TypeScript 或声明式格式。工具要求的 JavaScript、生成代码和第三方代码是具体例外，不能成为第一方业务回退到普通 JavaScript 的理由。

从 `strict` 开始，默认纳入 `noUncheckedIndexedAccess` 与 `exactOptionalPropertyTypes`；兼容障碍需要限定范围并说明原因。边界输入用 `unknown` 配合收窄和运行时校验，避免用宽泛 `any`、类型断言或忽略指令掩盖错误。检查覆盖应用、服务、测试和构建配置的 TypeScript 项目；由官方模板的项目引用或清晰的项目配置组织，不只检查界面目录。

构建、开发服务器和依赖管理由官方工具承担，协议校验、内容解析等通用能力使用成熟包。共享层只容纳实际跨入口复用的业务结构；服务端密钥与私有文件不进入前端变量或静态目录。

参考：[Vite 模板](https://vite.dev/guide/)、[TypeScript 严格模式](https://www.typescriptlang.org/tsconfig/strict.html)、[索引访问](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html)、[可选属性](https://www.typescriptlang.org/tsconfig/exactOptionalPropertyTypes.html)。

### 工具链迁移与任务缓存

替换工具链先核对官方迁移方案、发布状态、运行环境与现有插件兼容性，保留可复现的原配置和锁文件。审查迁移对项目命令、规则、类型、测试提供器、运行时集成及产物的实际影响；迁移工具生成的改动也须逐项复核，不以改命令名称证明行为等价。提交检查与 CI 继续连接项目维护的同一入口，保留暂存保护和原有质量要求。

组件拆分与工具替换各自建立验证基线，分别确认公开消费、交互、类型与生产构建等受影响行为；必要时用原方案对照定位差异。试验保留明确的退回方法，验证不支持采用时可继续使用原工具，不让一次工具试验决定组件架构或模板选型。各项目确认适合后独立采纳其通用配置，不共享另一仓库的本地路径、配置或验收记录。

涉及任务缓存时，核对实际输入、环境变量、依赖和输出的追踪方式，验证首次执行、再次命中、相关输入变化后失效，以及产物恢复；必要时以禁用缓存的执行对照结果。无法可靠追踪外部状态或副作用的任务按需禁用缓存，缓存命中不冒充本次实际执行。声称性能改善时使用相同环境和任务作可重复比较，正确性与速度分别报告。

参考：[Vite 迁移](https://vite.dev/guide/migration)、[统一工具链迁移示例](https://viteplus.dev/guide/migrate)、[任务缓存示例](https://viteplus.dev/guide/cache)。按实际所选工具查阅，不要求采用某个迁移目标。

## 组件选型与设计验收

先区分可编辑的视觉组件源码、处理键盘与焦点等交互的无样式行为层，以及项目面向业务的组件接口。成熟方案可能覆盖其中一层或多层；从官方资料确认实际采用的底层实现、兼容条件和维护方式，不因名称相同就混用不同实现。选择服从现有工程与产品需求，不把某个组件体系设为所有项目的默认答案。

沿用项目已有语义设计变量、字体、间距、密度与主题，按所选组件需要做有限映射，保留项目的视觉识别。先用一个实际流程做局部试样；涉及弹窗和选择器时，在真实弹窗中组合验证，不能只展示孤立组件。核对标签关联、表单值与提交、校验和错误提示，以及键盘操作、嵌套弹层、焦点进入与返回；组合适配须保留底层要求的属性、事件和元素引用。

在相同内容、交互状态、语言、主题与视口下保留修改前后截图，比较层级、间距、密度和一致性；同时验证长文案、窄屏及目标语言与主题组合。实际交互和人工视觉评审各自提供证据，检查或测试通过不能替代审美判断，截图也不能证明键盘和表单行为正确。

按任务约定完成试样验证后再推广。用户要求先确认效果时，保留可运行的本地试样与明确未验收项，等待效果确认再扩展范围；组件拆包、构建工具迁移等工程调整依据各自需求单独推进，不与视觉试样绑定交付。

参考：[可编辑组件源码](https://ui.shadcn.com/docs)、[行为层组合要求](https://www.radix-ui.com/primitives/docs/guides/composition)、[模态弹窗交互](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)。资料用于理解职责与验收，不要求选用同一套实现。

## 组件化与模块化

在首个可运行流程中示范职责分工。挂载入口负责启动，应用入口组合路由、页面和共享能力；页面组织当前任务，交互组件维护自身展示与短暂状态。业务规则、持久化和外部请求放在各自职责内，通过语义明确的操作交互。以实际复用和独立变更为依据拆分，无须预建完整分层目录，也不用文件行数作为设计标准。

先确定每份状态的唯一所有者和生命周期。局部状态靠近使用处，跨页面仍需保留的状态提升到共同所有者；只有跨层共享确有需要时才使用上下文，并按职责提供数据与操作。请求取消、过期结果和资源回收由拥有该请求的模块统一处理，保留清晰的导航与任务生命周期约定。避免把原入口整体搬进一个大 Hook，或通过传递大量内部状态、setter 与回调制造新的紧耦合。

拆分后用实际修改路径和既有行为验收：页面布局、业务规则或请求实现的变化各自集中，入口无需了解具体算法；跨页面草稿、偏好、异步取消和按需加载仍按原约定工作。模板也提供这样的可运行示例，项目架构说明记录职责与依赖方向，项目级技能按任务指向同一说明。检查选择与改动相关的行为，避免为匹配文件名或目录形状编写结构测试。

### 组件包与工作区边界

确有多个消费者、独立维护或分发需求时再建立组件包，不为整理目录预先引入多包仓库。包维护可复用界面与稳定公开入口，应用继续拥有业务状态、路由与产品配置；通过包清单的导出约定消费，避免深层源码引用或相邻目录穿透。用实际消费者验证入口、类型、样式与必要交互，而不是只证明包自身能检查。

React 组件包按消费契约声明 React 等宿主能力为对等依赖，并核对安装与构建后应用复用同一 React 实例。主题与其他共享上下文保持一致的提供者来源，不在组件包内附带另一套宿主或偏好存储。组件声明所需的语义 CSS 变量及样式入口，应用维护品牌值、主题选择和布局；保留原有变量与样式契约，避免把某个应用的设计和业务复制进通用包。

同工具链的内部消费可由应用编译组件源码；面向其他工具链或外部分发时，依据目标环境选择构建后的 JavaScript、类型声明和 CSS，明确依赖是否外置、导出入口及样式副作用。源码分发、构建成功与正式发布分别说明，发布沿用任务授权。工作区引用仅连接同一仓库的包，独立仓库各自维护完整上下文；跨仓复用通过明确的分发产物或通用模板，不依赖作者本机的相邻检出。

参考：[pnpm 工作区](https://pnpm.io/workspaces)、[React 重复实例](https://react.dev/warnings/invalid-hook-call-warning#duplicate-react)、[Vite 库构建](https://vite.dev/guide/build.html#library-mode)。方案按消费需求选择，不要求组件包必须单独构建或发布。

### 模块边界与架构检查

模块边界约束规定哪些模块可以引用哪些模块。先沿实际依赖审查稳定、可机械判断的要求，如禁止反向依赖、运行环境隔离和运行时循环依赖，再选择自动检查；项目元信息的单一来源可通过既有投影、类型或行为测试验证。状态归属、异步取消与交互正确性继续由行为测试和评审判断，静态依赖检查不替代这些证据。

优先复用框架、类型系统和现有 lint 规则；确实需要解析后的跨文件依赖图时，再引入成熟分析工具。导入路径的文本匹配不等于实际依赖解析，须核对工具如何处理路径别名、扩展名、路径规范化、重导出及动态导入；明确类型引用是否允许、检查的是运行时还是包含类型的依赖，按项目实际写法验证覆盖范围。解析与规则执行交给成熟工具，不自建依赖解析器。保留项目已有组织方式；已采用 FSD 时遵循其层、业务切片和公开入口，优先适配该约定的成熟检查器（如 Steiger），不把它设为所有项目的默认架构，也不为工具强行重排目录。

每项规则说明允许和禁止的依赖、检查入口及失败信息，以隔离合成正例和真实违规反例证明正常引用放行、违规被阻断。涉及跨文件关系时运行完整依赖检查，不能只检查改动文件就声称覆盖依赖图；提交前与 CI 调用项目维护的同一入口。规则和例外随职责变化维护，不用行数、目录快照或跨仓复制的检查结果证明架构质量。

参考：[Oxlint 受限导入](https://oxc.rs/docs/guide/usage/linter/rules/eslint/no-restricted-imports)、[循环依赖](https://oxc.rs/docs/guide/usage/linter/rules/import/no-cycle)、[依赖图规则](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)。另见 [FSD 组织方式](https://feature-sliced.design/docs/get-started/overview)。这些用于比较检查能力，不要求每个项目采用同一架构或工具。

## 从第一批代码启用质量规则

使用当前官方推荐配置建立起点，再显式开启适合所选框架的正确性、可疑行为、类型、异步和可访问性规则。检查实际启用的插件与规则，不能把默认少量规则或“已经安装工具”称为严格基线。

React 项目包含 Hooks 调用与依赖检查、适用的 JSX 可访问性规则；有异步代码时使用兼容的类型感知规则发现悬空 Promise、错误的异步回调及不安全类型流。Oxlint 的类型感知能力需要核对配套包与所选 TypeScript 的兼容性，不能用尚未验证的实验功能替代标准类型检查。显式配置插件时核对是否覆盖了工具默认启用项。

将检查警告作为提交与 CI 失败处理。基于需求选择规则，不用无差别开启所有争议规则代替工程判断；必要例外限定到具体规则和位置，说明原因，不全局放宽后留待未来修复。

Oxfmt 的同一配置服务编辑器、开发命令、提交前检查和 CI；CI 使用只检查模式，自动修复限定在格式及安全修复。格式、静态检查与类型检查各负其责，命令在项目清单维护。

参考：[Oxlint 配置](https://oxc.rs/docs/guide/usage/linter/config)、[规则](https://oxc.rs/docs/guide/usage/linter/rules)、[类型感知](https://oxc.rs/docs/guide/usage/linter/type-aware)、[Oxfmt 配置](https://oxc.rs/docs/guide/usage/formatter/config.html)、[Oxfmt 暂存与 CI](https://oxc.rs/docs/guide/usage/formatter/ci)。

## 提交前检查是工程基础

使用 Husky、lint-staged 或工具链已有的成熟等效方案。将暂存检查暴露为项目清单中的可执行命令，钩子只调用该入口，便于贡献者发现和排查；不要同时维护两套等价钩子体系。提交钩子安装接入正常依赖安装流程，使新克隆的仓库可复现；源码及命令随仓库维护，不依赖作者本机全局设置。

暂存格式与静态检查由工具管理文件选择、备份、重新暂存和恢复；重叠写文件任务串行执行，保留部分暂存保护，避免自行 `git add .` 或实现另一套暂存恢复脚本。

类型检查运行整个适用 TypeScript 项目，避免把暂存文件名追加给 `tsc` 而绕开项目配置。说明各项检查针对本次暂存内容还是整个工作树；工作树检查通过不能冒充待提交内容通过。检查待提交内容时，采用工具正式提供的暂存隔离选项，在隔离有效期间运行整个项目的类型检查。使用 lint-staged 时核对所选版本的 `--hide-all` 等正式选项；核实未暂存、未跟踪与忽略文件各自的处理范围，准确说明剩余边界，由 CI 对最终提交兜底。

从没有本机钩子配置和生成钩子的全新工作副本开始，只按文档执行正常安装，再做真实提交。单独手动运行 `prepare` 或看到钩子文件，不证明新克隆能自动接通。核对所选包管理器的安装生命周期及脚本策略；验证中绕过的安装步骤不能当作默认行为。

在临时 Git 仓库分别验证：有效提交成功；真实类型错误和静态检查违规使提交失败且 HEAD 不变；暂存版本有类型错误而未暂存修改已修好时，提交仍失败；部分暂存文件的未暂存改动被保留且没有进入提交。只用 `exit 1` 证明钩子接通不算质量规则验收。格式允许自动修正时，证明提交内容已规范化，或检查失败确实阻断。

CI 检出最终提交后，再执行完整格式、静态、类型、行为测试和生产构建。本地钩子可以被跳过，因此与 CI 共同约束交付，不能宣称某一次钩子成功保证全部提交质量。

参考：[Husky 初始化](https://typicode.github.io/husky/get-started.html)、[lint-staged](https://github.com/lint-staged/lint-staged)、[TypeScript 项目命令](https://www.typescriptlang.org/docs/handbook/compiler-options.html)。

## 多语言从界面入口接通

根据受众确定起始语言、支持范围和回退语言，采用框架内置或 i18next、FormatJS 等成熟方案。界面文案放在翻译资源，用有含义的键引用。持续维护的应用按语言独立资源，注册入口只组装；规模增长后再按业务分组，配合类型或工具检查文案键的完整性。小型示例按维护需要取舍，不为拆文件额外引入远程加载。完整句子、插值和复数交给库，日期、数字等交给区域格式化能力。代码标识、资料原文和用户生成内容不因切换界面语言而擅自翻译。

首个代表性界面用两种目标语言验证真实切换，包含标题、表单标签、按钮、提示、错误及无障碍名称。同步 `html.lang`，目标语言需要时处理 `dir`；明确显式选择、保存偏好与浏览器语言的优先级，并验证缺失翻译或失效偏好的回退。覆盖协议校验、服务端与第三方错误经过的真实失败路径，不仅翻译组件内文案。用稳定错误码或类别选择本地化提示，原始诊断按需要保留为辅助信息；不能把库或上游返回的任意消息直接当作界面翻译。仅预留语言字段而页面仍硬编码不算接通；完整翻译规模按产品范围推进。

参考：[i18next 写法](https://www.i18next.com/principles/best-practices)、[资源分组](https://www.i18next.com/principles/namespaces)、[配置与回退](https://www.i18next.com/overview/configuration-options)、[区域格式](https://www.i18next.com/translation-function/formatting)、[网页语言声明](https://www.w3.org/International/questions/qa-html-language-declarations.en)。

## 外观模式、主题与用户定制

把亮色、暗色、跟随系统这组外观模式，与品牌配色、字体或密度这类主题选择分开。通过语义设计变量和成熟主题机制作用于同一套组件；已有设计系统优先复用，不能靠各组件散落的颜色覆盖实现暗色。

首版接通亮色、暗色和跟随系统，正确响应系统变化并尊重用户显式选择。主题配置支持扩展命名主题以及产品允许的用户覆盖项，定义可持久化的偏好、有效值、回退与恢复默认行为。通过两个小型命名主题和一个允许覆盖项，证明配置确实影响组件，且能保存、回退和恢复；不以空类型或未使用变量冒充能力。正式设置入口及完整编辑器按产品范围交付，基础机制的试用界面不等于完整定制产品，也不应未经需求开发主题市场或任意 CSS 编辑功能。

核对成熟库的能力是否依赖服务器渲染、静态生成或特定宿主，再采用对应首屏机制。检查实际页面初次载入与刷新是否闪烁，必要时延迟应用模块以观察绘制前状态；组件挂载完成后的检查不能代替首屏验证。涉及服务端渲染时验证初始外观和客户端接续一致。语言、外观及主题偏好可独立组合；切换后，正文、表单、代码、焦点、禁用与错误状态仍清晰可读。用户允许覆盖颜色时，同时验证极亮、极暗边界，不能把颜色格式合法等同于文字可读；存储失败提示覆盖所有偏好入口。

参考：[Radix 主题结构](https://www.radix-ui.com/themes/docs/theme/overview)、[系统外观与首屏](https://www.radix-ui.com/themes/docs/theme/dark-mode)、[MUI 模式与偏好](https://mui.com/material-ui/customization/dark-mode/)。这些用于说明机制，不要求所有项目选择同一个组件库。

## 首页与核心路径

新建独立站点或应用、重做产品入口时，先说明首页服务谁、帮助他完成什么。介绍和转化为主的站点需要产品介绍页；Agent、聊天或工作台类应用通常需要能直接开始任务的应用首页。两者并存须有明确分工，不把每个产品都套成营销长页，也不把某条记录的详情当作整个应用的默认门面。

首屏用简短说明、一个突出的核心操作和必要引导回答“这是什么、可以做什么、怎样开始”。示例只降低起步负担，不替代主要操作；内容和能力来自真实实现，不虚构会话、统计或已接通的模型。回访用户能继续已有工作，同时始终能回到首页、开始新任务和访问历史；回首页与新建不能隐式删除记录或丢失草稿。

先画通首页、任务页和历史之间的最短路径，再调整页面外观。复用适合框架的成熟路由或导航能力，按实际需要支持直达、刷新与浏览器返回；不为装饰性链接引入整套流程，也不自行实现通用路由器。验证空记录、已有记录、回首页、继续任务、导入与错误、窄屏和语言主题组合，确保首页在实际有数据的应用中仍可到达，而不只是一个空状态。

导航时明确草稿、任务状态、阅读位置和输入焦点的归属：新页面从核心内容起点进入，浏览器返回能继续原阅读位置；新任务入口能实际开始输入，菜单关闭不抢走目标焦点。离开页面、取消或转去另一操作后，旧异步结果不能覆盖新任务、抢回页面或唤起已经放弃的界面。根据业务选择取消或继续后台任务，并验证对应行为。

## PWA 与移动使用

独立 Web 应用在早期确认手机访问、重复使用和弱网场景，判断是否需要 PWA（可安装到设备并以应用窗口打开的 Web 应用）。明确安装基础、离线阅读、写入同步各自的交付范围；可安装不等于完整离线能力，普通网页或局部修复不因此扩建后台任务。

需要安装体验时，清单中的名称、说明和语言从项目元信息派生，图标沿用品牌源文件并用成熟工具生成所需尺寸及可遮罩版本。核对目标浏览器的安装条件、HTTPS、入口地址和作用范围；按浏览器实际能力提供安装按钮或简短手动说明，由使用者主动触发。独立窗口中仍可完成导航、导入和导出，安全区、屏幕旋转、动态视口、软键盘及深浅色状态栏不遮挡主要操作。核实浏览器与安装容器的记录延续方式，本地存储不冒充跨设备同步。清单和图标齐全不代表已经完成手机安装验收。

只有离线范围需要时才接入服务工作线程（浏览器中可拦截请求并管理缓存的后台脚本），优先框架集成、维护中的 PWA 插件和 Workbox 等成熟方案。先划定公开静态资源、私有数据和联网请求的边界，默认不缓存凭据、鉴权接口、生成内容及私有本地交换路径；明确首次访问、离线打开、恢复网络及数据清理的行为。离线写入或模型请求队列需要独立业务设计，不因安装功能自动加入。

启用缓存后同时设计更新：新版本到达时保留草稿和进行中的任务，由使用者选择安全的更新时间，使用成熟机制清理旧缓存。开发环境按需禁用服务工作线程，防止旧产物干扰调试。生产验证覆盖清单与图标、深层地址、目标移动视口、安装入口及实际声明的离线和升级行为；模拟的浏览器能力、自动化引擎与实体设备安装分别说明。

参考：[安装条件与能力边界](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)、[Vite PWA](https://vite-pwa-org.netlify.app/guide/)、[Workbox](https://developer.chrome.com/docs/workbox/)。

## 设计、响应式与测试

选择符合产品用途的优秀设计参考，先确定内容层级、阅读宽度、导航和主要操作，形成自己的设计变量与基础组件。用实际长度的合成中文、其他目标语言、代码和长链接验证；布局适应内容和设备，局部代码滚动不撑宽整页。

用 Vitest 测试项目分别覆盖 Node 业务、正式浏览器提供器中的真实组件及实际服务运行时。需要导航、前后端或生产产物全流程时，复用成熟端到端工具；Cloudflare 等平台使用官方运行时工具。模拟外部模型可以稳定测试错误和取消，但不能当作真实模型验收。

验收同时覆盖语言、外观及主题的代表性组合，而不是每项各截一张默认截图。至少检查语言切换与回退、偏好刷新恢复、系统外观变化、用户覆盖与恢复默认、首屏、表单和异步状态，以及手机/平板/桌面、断点两侧、长文案、文字放大、键盘与触摸目标。使用实际字体和组件验证；长文案包括没有空格的合法内容，异步场景包括等待期间继续编辑、取消与迟到响应，弹窗关闭后返回实际触发入口。避免无意义地穷举所有组合；以边界和关键用户流程选取案例。

构建完成后检查可处理的体积与兼容告警。按实际使用时机拆分非首屏功能，验证延迟模块确实按需请求；不只拆文件，也不靠抬高阈值隐藏问题。

记录实际视口、运行环境和结果；浏览器移动模拟不等于真机、软键盘或触摸硬件验收。结构检查、依赖解析、代码测试和实际应用操作分别报告，未执行的部分保持未验证。

参考：[Vitest 测试项目](https://vitest.dev/guide/projects)、[Browser Mode](https://vitest.dev/guide/browser/)、[Playwright](https://playwright.dev/docs/intro)、[WAI 页面结构](https://www.w3.org/WAI/tutorials/page-structure/)。
