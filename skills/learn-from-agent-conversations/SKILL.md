# 从 Agent 对话中学习

把对话中“没理解”的地方变成可理解、可继续追问的解释。防止知识的诅咒：讲解者已经熟悉的前提，学习者未必知道。目标是减少理解障碍，而不是不断增加知识点。

## 找到当前卡点

从用户的追问和实际可见的前文中，确定正在解释的原句、结论、步骤或代码，以及用户想弄清的关系：它是什么、为什么需要、怎样发生，或与另一概念有什么区别。

目标明确时直接解释；多处都可能是所指内容时，只问一个具体澄清问题。缺少原文时请用户提供相关片段，不虚构对话历史。通常不需要仓库、代码差异、工具调用或完整知识水平调查。

把用户明确表达或通过回答展示的知识当作起点，不根据职业、使用过的软件、见过的术语或前文已出现过某个词，假定其已经理解。

**完成标准**：知道这次回应要解决哪个具体疑问，以及能够使用哪些上下文。

## 先回应疑问，再按需展开

先用简短、直接的说法回答当前问题，再用贴近原文的一个例子或具体步骤说明。围绕一个主问题展开，信息量随用户反馈调整；一般先给能建立理解的最小解释，而非完整教材。

优先复用当前对话里的对象、例子和已经解释过的概念。用户仍不理解时，换一种表达、缩小步骤或补齐缺失前提，而不是把原文换成更抽象的同义词。

Agent 先前的内容也可能有错。发现错误或证据不足时先更正或标明不确定，再解释可成立的部分；不要为了维持原回答而补造前提。区分原文事实、帮助理解的假设和类比。

## 必要的新概念，就地解释

每次准备引入新名词，先判断当前疑问是否真的需要它。能用具体行为说明的，优先说清“什么发生了、对什么产生了影响”。无助于当前理解的概念留待需要时再讲。

必要概念首次出现时，紧邻说明它解决什么问题、用通俗话怎样理解，以及它与当前例子的对应关系。小概念可以用一句话交代；复杂概念拆成可连接的小步骤。只展开缩写、换一个术语或循环定义，不算解释。

如果解释还需要另一项未知知识，先补最小前提，再回到原问题，避免形成一串未解释的术语。边界、反例和图示也遵守这一规则；不要为了一个非必要对比再引入一套新知识。

类比用于帮助理解，应说明对应关系；仅在会影响判断时补充它不适用的边界。概念表和外链可以帮助回查，不能代替当前回应中的必要说明。

**完成标准**：关键推理没有依赖未说明的前提，新概念能够与当前问题连接，而不是产生更多悬而未解的名词。

## 用互动调整深度，不强制考核

互动可以是追问、换例子、共同拆解，也可以是用户自愿的复述或预测。需要确认理解时，一次选择一个轻量问题；用户要求直接解释、不要提问或不要练习时，尊重该方式。

从用户的回答定位具体误解，补讲缺失的一步，然后继续原问题。不要仅问“懂了吗”，也不要把理解困难归因于学习者，或用“显然”“很简单”跳过必要解释。

当前疑问已得到回应，就在适当位置停下，给用户继续追问的空间。用户希望深入时再扩展，不默认安排课程、长报告、作业或复习日程。

未观察到回答或练习结果时，说明已提供解释，不宣称用户已经掌握。用户表示理解时可据此继续，但不据此建立永久能力档案。

## 语言与准确性

跟随用户指定的语言。中文讲解以自然中文组织句子，有成熟中文译法时优先使用通行名称。需要对照原文时，首次可附英文原名，后续统一称呼，避免反复堆叠双语或中英术语拼接。

没有稳定译法、原名更通行准确或翻译会削弱含义时，保留原名并说明用途。代码标识、公式符号、命令、路径和协议字段保持准确；保留原名不代表可以省略必要解释。

解释结论的可核对依据与步骤。只使用实际可见或获准读取的内容；如果判断依赖外部事实，按任务需要核实，并说明已确认与仍不确定的部分。简化语言不等于改变原有条件、因果或适用范围。

## 需要更完整的学习材料时

- 用户希望系统理解一项代码改动时，读 [代码改动走读](references/code-changes.md)。代码只是学习材料的一种，不是本技能的进入条件。
- 用户要求保存笔记、完整报告或专题文档时，读 [学习材料整理](references/learning-notes.md)。沿用指定的交付形式，已有材料优先局部更新。

解释与执行是不同请求。用户询问一个操作或命令的含义，不因此授权执行它、修改环境或写入外部服务；需要操作时沿用原任务的授权范围。
