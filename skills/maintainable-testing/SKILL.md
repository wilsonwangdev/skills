# 维护可持续的测试工程

让每个测试有明确的故障判据，让新增同类场景复用工程入口。先看现有保障，再选择保留、改写、合并或暂缓；文件数量、通过率和覆盖率本身不能证明测试有价值。

新建或迁移应用时的测试基线（运行器选型、提交检查、浏览器验收）由 `build-maintainable-app` 决定；本技能只处理既有测试体系的审计、收敛与验证。

## 建立执行与风险基线

读取项目约定、运行器配置、测试目录、清单和 CI 的真实调用链。区分测试场景、共享夹具、命令入口和需要专用环境的验收。检查文件发现规则、模块与进程隔离、顶层副作用，以及网络、原生工具、认证和硬件要求，实际确认默认命令运行什么。

记录本次会影响的用例身份与结果、测试命令和重复初始化。每项整理说明要保住的行为，以及能让对应检查失败的故障。选择可独立验证的一片；运行器迁移、目录搬迁、场景改写和删除分别说明必要性。已有未合并工作与项目功能保持原范围。

## 选择适合的保障

- 类型与稳定结构约束优先交给现有编译器和静态规则。新增规则前扫描真实候选与合法反例，证明它补了缺口，再接入已有检查链；报错定位文件和规则。仅为替换几条断言，不另建检查脚本、解析器或规则例外清单。
- 行为回归聚焦状态分支、数据转换、失败后的停止、并发时序和可观察副作用。断言公开结果、发出的请求与禁止发生的操作，减少对源码文本、私有函数调用顺序和偶然标记的依赖。
- 配置、生成产物与公共协议可能本身就是受测契约；读取 JSON 或文件不自动等于低价值。安全控制、持久化兼容和原生边界需要相应的行为证据，静态结构不能代替它们。

删除或合并断言前，指出等价保障在哪里、如何实际发现原故障。保障尚未落地时保留现有测试；只是不被当前入口调用，也不构成删除依据。

## 让场景复用夹具

从已发生的重复中提取按边界或测试种类组织的共享支持，测试文件保留自己的输入、场景和断言。优先使用运行器及成熟库的隔离、转译、DOM 和 mock 能力；复杂的自制模块加载器应先评估维护成本和替代方案，不把本次整理扩成全仓迁移。

替身放在外部边界，保留受测模块和必要的序列化路径。未声明的调用要明确失败；按真实契约区分允许返回空值的操作、预期服务失败和夹具自身异常。共享清理负责恢复全局状态与资源；提取后的夹具不应成为包含全部业务状态的万能对象。

## 收敛发现与执行入口

沿用当前运行器的标准发现与过滤能力。项目入口按真实运行环境或验收层分组，同类新文件自动参与对应入口；定向回归用路径或运行器过滤，不为每个功能登记新的清单命令。

便携检查与原生、认证、网络或硬件验收保持明确边界，CI 复用同一分层入口。验证 glob、辅助文件和顶层初始化，避免误收昂贵测试或遗漏新增文件；保留需要的文件与进程隔离。若工具缺少能力，先比较惯用目录调整和成熟配置方案，再考虑必要适配，不自建另一套测试运行器。

## 用反证完成试点

比较整理前后的实际用例集合、失败与跳过，解释每个差异。临时增加一个同类场景，证明它无需清单登记即可运行；以代表性的错误输入、故障注入或变异，证明关键回归仍会失败，修正后再通过。探针与当次日志留在隔离临时目录，恢复命名文件后核对工作树；不把验证手段扩成常驻脚本。

报告入口、重复夹具和受保护行为的前后变化，列出实际命令与环境边界。耗时比较注明环境和样本；一次本机观察不外推 CI 提速，应用测试通过也不等于技能有效率。项目的长期约定更新已有维护入口，命令与版本仍由可执行配置维护；通用经验用合成案例回馈技能，真实项目记录留在项目或评审中。

方法参考：Robin Wieruch，[Testing AI-Generated Code: Lint the Pattern, Test the Decision](https://www.robinwieruch.de/testing-ai-generated-code/)。本文工作流另补充了执行入口、环境边界与渐进迁移的验证要求。
