# 个人编码与审查风格

让使用者能从完整差异中判断改动的必要性、职责和维护成本。以下是本技能的默认取舍，当前用户要求与项目约定优先；具体接口和职责依据需求与代码确定。

## 先明确任务与现场

区分本次是审查、方案评估还是实施。审查与评估默认只读，给出问题、依据和建议；用户要求修复或实施时再修改。审查发现的问题不自动扩大操作授权。

按使用者和项目约定选择工作区与任务分支；未指定且项目允许时，本技能偏好在主工作区展示任务改动。先核对基线、分支、暂存区和已有修改，保护无关工作。完整差异包括新增文件；提交、推送与发布分别遵循当前授权。

## 用实际需求决定改动范围

先说明用户要改变的可观察结果，沿调用链核对生产者、消费者和失败路径。普通局部修复沿用已有边界；准备调整共享接口、职责或生命周期时，再深入比较保留现状、局部适配和结构调整。

- 核对当前实现、实际依赖版本和已接通的行为。已有协议、扩展点、类型与工具优先复用，同时检查语义、依赖和状态归属是否匹配；名称或位置不匹配的封装也有维护成本。
- 说明谁实际需要新增语义，不改会怎样，更小方案具体缺少什么。评估兼容性、其他调用方、测试迁移和回退成本；机械修改也占用审查与维护成本。
- 实施前简述推荐方案、收益和影响面，在已有授权内继续。发现新的迁移成本时重新核对必要性；减少代码仍须保留权限、生命周期和兼容保障。

**实施判断完成条件**：能指出现有接口无法表达的实际需求、更小方案为何不足，以及收益是否值得承担受影响调用方的迁移成本。证据不足时保留现有边界或缩小范围；已有明确选择按用户要求执行。测试通过不能替代这项判断。

## 用有条件的示范检查取舍

| 条件 | 推荐做法 | 应避免的做法 |
| --- | --- | --- |
| 多个入口共用执行接口，只有一个入口需要额外的界面事实，其他执行语义相同 | 先检查该入口已有的宿主扩展点，将快照和适配限制在实际消费者 | 仅为传递这份信息扩大共享入参，让所有入口和测试迁移 |
| 多个入口都需要同一组任务参数，且必须保持一致校验，现有接口已经表达不足 | 说明共同语义与迁移成本后引入结构化输入，验证各入口行为与兼容性 | 为减少 diff 把必需数据塞进隐式全局状态，或一概拒绝接口调整 |
| 多处输出相同的错误结构，已有辅助函数位于某个业务模块 | 核对它是否只负责响应编码、是否附带业务依赖，再决定复用或局部整理归属 | 只因返回值相同就调用，忽略额外副作用；或立刻新建通用错误框架 |

这些示范用于判断适用条件，不固定某种参数形式、文件位置或模块划分。新增职责要有实际消费者或故障依据；一个更短的 diff 也可能保留了不合理的边界。

## 保留能发现故障的保障

先确认现有测试保护什么，再补缺口。类型与稳定结构约束交给现有编译器和检查；行为回归聚焦状态分支、边界转换、禁止发生的副作用及真实故障。复用现有运行器和外部边界夹具；测试体系整顿按独立需求确定范围。

例如修复“校验失败后仍写入”，应验证失败结果和存储未发生变化；只匹配错误文案或私有函数调用次数不足以保护这个故障。精确协议、额度与错误语义仍值得精确断言。删除或合并测试时指出等价保障；新增文件、测试数量和通过率都不能单独证明质量或膨胀。

## 让长期文档保持可信

长期上下文记录职责、不变量和非显然的决策理由。版本、构建标识、命令和数值优先指向可执行配置或权威契约；确属公开承诺时说明含义。核对日期、跨仓提交、迁移过程和重验日志留在任务证据中。注释解释原因与边界，避免复述实现。

## 独立判断最终差异

分别审查行为正确性与设计必要性。先给具体问题、影响和依据，再给最小修正建议；用户质疑设计时回到需求和源头，不为已有代码补理由。

交付时说明改动为什么值得、实际验证支持到哪里，以及关键未覆盖项和授权状态。维护者应能判断新增职责为何属于当前项目、其他调用方付出了什么成本，以及为何不选更小方案。局部检查通过不等于整体完成。
